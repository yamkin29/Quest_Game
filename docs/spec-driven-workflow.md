# Spec-Driven Development: работа над фичами с AI-агентом

Инструкция описывает процесс разработки фич по методологии Spec-Driven Development (SDD): сначала спецификация, затем технический план и задачи, и только потом код. Процесс заточен под работу с AI-агентом (ZCode и совместимые), но работает и без него.

## Зачем это нужно

- Агент получает точный вход: не «сделай сохранение прогресса», а спецификацию с проверяемыми критериями приёмки — меньше домыслов и переделок.
- Критерии приёмки из спеки почти один в один превращаются в тесты (unit, component, e2e).
- План и задачи — точки контроля: человек утверждает дизайн до кода, а не ревьюит готовые тысячи строк.
- Спеки остаются в репозитории и служат документацией: почему фича такая, какая она была на момент разработки.

## Где что лежит

| Путь                                        | Назначение                                    |
| ------------------------------------------- | --------------------------------------------- |
| `docs/spec-driven-workflow.md`              | эта инструкция                                 |
| `development_plans/<feature>/spec.md`       | спецификация фичи: что и зачем                 |
| `development_plans/<feature>/plan.md`       | технический план: как                          |
| `development_plans/<feature>/tasks.md`      | упорядоченный чек-лист задач                   |

`<feature>` — короткое имя фичи на английском в kebab-case: `save-progress`, `inventory`, `hint-system`.

Правила процесса (Mantine-first UI, словарная локализация, формат коммитов, проверки) описаны в `AGENTS.md` — эта инструкция их не дублирует, а ссылается.

## Фазы

### 0. Идея

Фиксируем идею одной строкой (issue или черновик в `development_plans/`). Если идея не умещается в одну строку — это уже повод начать спеку.

### 1. Спецификация — `spec.md`

Отвечает на вопросы «что делаем и зачем», без реализации. Заполняем по шаблону из конца этого документа.

Ключевые требования:

- **Критерии приёмки проверяемы.** Не «удобный интерфейс», а «после перезагрузки страницы восстанавливается последняя сцена, что проверяется e2e-тестом».
- **Сценарии описаны как взаимодействие игрока с игрой**: действие игрока → ответ игры. По желанию — в виде sequence-диаграммы (mermaid), это и есть system sequence diagram из анализа.
- **Out of scope указан явно**: что сознательно не делаем в этой фиче.
- **Открытые вопросы закрыты до фазы плана.** Если вопрос нельзя закрыть — фиксируем решение по умолчанию и помечаем как пересматриваемое.

Спеку составляет агент, утверждает человек. Пока спека не утверждена — кода нет.

### 2. Технический план — `plan.md`

Отвечает на вопрос «как это устроено в этом проекте». Заполняет агент, утверждает человек. Обязательные разделы см. в шаблоне: затронутые модули FSD, изменения состояния игры (`GameState`, actions редьюсера), новые ключи i18n (сразу для `ru` и `en`), используемые компоненты Mantine, стратегия тестов, риски.

Здесь же — мост от сценариев спеки к коду: каждая системная операция из сценария (например, `submitCommand`) получает описание нового поведения или новой операции.

### 3. Задачи — `tasks.md`

План нарезается на упорядоченные задачи, каждую можно выполнить и проверить независимо:

- формулировка «что сделать» + «когда задача считается сделанной»;
- задача завершается коммитом; тип коммита указан в задаче (`feat(i18n): ...`, `test(e2e): ...`);
- тесты пишутся в той же задаче, что и код, который они проверяют; e2e-сценарии из спеки — отдельными задачами;
- первая задача обычно подготовительная (типы, ключи локали), последняя — прогон полного валидатора и сверка со спекой.

### 4. Реализация с агентом

- Агент берёт **одну** невыполненную задачу из `tasks.md`, реализует, запускает целевые проверки (тесты модуля, `npm run check`), делает коммит по правилам `AGENTS.md`.
- Задачи, меняющие игровое поведение, реализуем по TDD-циклу из [docs/tdd-workflow.md](tdd-workflow.md) (список поведений → Red → Green → Refactor). Связь уровней: SDD описывает процесс фичи целиком, TDD — тактику внутри задачи; список поведений из шага 0 TDD берётся из критериев приёмки спеки.
- Человек смотрит результат после каждой задачи (или небольшого блока однородных задач) — так отклонения дешёвые.
- Агент не пушит и не переходит к следующей задаче без подтверждения, если человек этого просит.
- Хуки husky (lint-staged, commitlint) работают как обычно; проверки не отключаются.

### 5. Приёмка и завершение

1. Прогоняем `npm run validate` (линтер + типы + тесты + сборка); после крупных рефакторингов — `npm run check:react`.
2. Прогоняем e2e-сценарии фичи: `npm run test:e2e` (со сканами axe).
3. Сверяем фактическое поведение со `spec.md` пункт в пункт; расхождения либо чиним, либо оформляем как осознанное отклонение с правкой спеки.
4. Отмечаем все задачи в `tasks.md`, при необходимости обновляем `README.md` и документацию в `docs/`.
5. Папку фичи в `development_plans/` оставляем в репозитории — это архив решений, а не мусор.

## Правила работы со спецификацией

- Спецификация — источник истины. Если в ходе реализации выяснилось, что спека неполна или неверна — сначала правим спеку и согласуем правку, потом меняем код. «Код уже так написал» — не аргумент.
- Спека не описывает реализацию (файлы, функции, компоненты) — это задача плана. Спека описывает поведение и критерии.
- Одна фича — одна папка. Переделка существующей фичи живёт в новой папке и ссылается на старую.

## Промпты для агента

Готовые формулировки (подставляйте своё имя фичи):

- Начало фичи: «Прочитай docs/spec-driven-workflow.md и AGENTS.md. Начинаем фичу save-progress: помоги составить development_plans/save-progress/spec.md по шаблону. Задай вопросы по неясным пунктам, код пока не пиши.»
- Утверждение спеки: «Спека утверждена. Составь plan.md и tasks.md: затронутые модули FSD, изменения GameState, ключи i18n для ru и en, стратегия тестов. Код не пиши.»
- Реализация: «Открой development_plans/save-progress/tasks.md и выполни следующую невыполненную задачу по правилам AGENTS.md. После — целевые тесты и коммит. К следующей задаче не переходи.»
- Приёмка: «Фича готова. Прогони npm run validate и e2e, свери фактическое поведение с development_plans/save-progress/spec.md и доложи расхождения.»

## Шаблоны

### spec.md

```markdown
# <Название фичи>

## Проблема и цель
Что сейчас неудобно или невозможно и зачем это делать.

## Пользовательские сценарии
Формат: действие игрока → ответ игры. Можно mermaid-диаграммой.

## Критерии приёмки
- [ ] Проверяемое утверждение 1
- [ ] Проверяемое утверждение 2

## Вне объёма (out of scope)
Что сознательно не делаем.

## Открытые вопросы
Вопросы, которые нужно закрыть до плана, и их решения.
```

### plan.md

```markdown
# План: <фича>

## Затронутые модули (FSD)
app / pages / widgets / features / entities / shared — какие и почему.

## Изменения состояния
Новые поля GameState, новые actions редьюсера, переходы inputMode/status.

## i18n
Новые ключи словарей (ru + en), переиспользуемые существующие.

## UI
Компоненты Mantine, макет, поведение на мобильных.

## Стратегия тестов
Unit (движок), component (виджеты), e2e (сценарии из спеки + axe).

## Риски и альтернативы
Что может пойти не так, какие варианты рассматривались.
```

### tasks.md

```markdown
# Задачи: <фича>

- [ ] 1. Подготовка: типы, ключи i18n (ru + en) — `feat(i18n): ...`
- [ ] 2. <Шаг> Готово, когда: <критерий> — `feat(game): ...`
- [ ] 3. <Шаг> Готово, когда: <критерий> — `test(e2e): ...`
- [ ] 4. Прогон npm run validate, сверка со спекой — `chore: ...`
```
