# Quest Game Web — Implementation Plan

## 1. Цель проекта

Преобразовать текущий консольный TypeScript-квест в одностраничное React-приложение с полноценным веб-интерфейсом, сохранив сюжет, игровую логику и ощущение работы с терминалом.

Итоговая страница должна содержать:

- адаптивный `Header` с названием игры;
- переключатель светлой и тёмной темы;
- переключатель русского и английского языка;
- центральное консольное окно с историей сообщений;
- строку ввода команд и ответов;
- `Footer` с информацией о проекте;
- возможность начать игру заново после победы или смерти.

## 2. Принятые технические решения

| Область | Решение | Почему |
| --- | --- | --- |
| Сборка | React + TypeScript + Vite | Проект полностью клиентский; SSR и серверная часть не нужны |
| Состояние игры | Чистый TypeScript-движок + `useReducer` | Логику можно тестировать отдельно от React |
| UI-библиотека | Mantine (`@mantine/core`, `@mantine/hooks`) | Готовые доступные компоненты, layout-примитивы и встроенная система темы |
| Иконки | `@tabler/icons-react` | Хорошо сочетается с Mantine и поддерживает tree-shaking при прямых импортах |
| Дизайн-токены | Переданный набор из `docs/design-tokens.css` | Единственный источник цветов, типографики, размеров, радиусов и теней |
| Стили | Mantine Styles API + CSS Modules | Mantine отвечает за дизайн-токены и базовые состояния, CSS Modules — за уникальный вид консоли |
| Локализация | Типизированные словари без внешней библиотеки | Два языка не требуют тяжёлой i18n-системы; типы проверят полноту переводов |
| Тема | `MantineProvider` + Mantine color scheme API | Не дублируем готовый механизм библиотеки собственным провайдером |
| Настройки | Mantine `useLocalStorage` для языка | Настройки синхронизируются между вкладками и сохраняются между запусками |
| Хранение настроек | Mantine color scheme manager + версионированный ключ языка | Тема и язык сохраняются между запусками |
| Тестирование | Vitest + React Testing Library | Хорошо интегрируются с Vite и подходят для движка и интерфейса |

### Почему не Next.js

Игра не требует серверного рендеринга, API, базы данных или маршрутов. Vite даст более простую архитектуру и позволит сосредоточиться на React, TypeScript и интерфейсе.

### Как будет использоваться Mantine

Mantine становится основой интерфейса, а не дополнительным набором отдельных кнопок:

- `MantineProvider` и `createTheme` задают тему приложения;
- `localStorageColorSchemeManager` сохраняет выбранную цветовую схему;
- `useMantineColorScheme` и `useComputedColorScheme` управляют корректным переключением light/dark/auto;
- `AppShell` формирует Header, Main и Footer;
- `Container`, `Stack`, `Group`, `Paper`, `Text` и `Title` формируют layout;
- `ScrollArea` используется для истории терминала;
- `TextInput`, `Button` и `ActionIcon` используются для ввода и действий;
- `SegmentedControl` используется для доступного переключения RU/EN;
- `Tooltip`, `VisuallyHidden` и стандартные focus-состояния Mantine помогают с доступностью.

Уникальный sci-fi вид консоли будет добавляться через CSS Modules и Mantine Styles API. Мы не будем переписывать базовые кнопки, поля ввода, переключатели и layout-примитивы вручную.

### Как будут использоваться дизайн-токены

Исходный набор сохранён без изменения значений в [`docs/design-tokens.css`](./design-tokens.css), а правила интеграции описаны в [`docs/DESIGN_SYSTEM.md`](./DESIGN_SYSTEM.md).

- `createTheme` связывает палитру, типографику, spacing, radii и shadows с props компонентов Mantine;
- `cssVariablesResolver` публикует семантические `--app-*` переменные для светлой и тёмной темы;
- dark theme строится только из уже переданных цветов и не вводит новые hex-значения;
- CSS Modules используют семантические или Mantine-переменные вместо сырых значений;
- готовые Mantine-компоненты расширяются через Styles API, чтобы применять named radii и состояния cyan signal/edge;
- пока лицензированные файлы Roobert не добавлены, работает указанный в токене fallback stack.

### Почему сообщения нельзя хранить готовыми строками

Если положить русскую строку прямо в историю консоли, после переключения на английский уже показанный текст останется русским. Поэтому движок будет возвращать ключи сообщений:

```ts
interface GameMessage {
  id: string;
  key: MessageKey;
  kind: "story" | "choice" | "input" | "system" | "error";
  params?: Record<string, string | number>;
}
```

React будет переводить ключи во время отображения. Благодаря этому вся история мгновенно меняет язык.

## 4. Модель данных

Предварительная модель состояния:

```ts
type Room =
  | "starship"
  | "temple"
  | "livingRoom"
  | "dangerRoom"
  | "questRoom"
  | "otherShip";

type GameStatus = "playing" | "won" | "dead";
type InputMode = "continue" | "choice" | "answer" | "finished";

interface GameState {
  room: Room;
  status: GameStatus;
  inputMode: InputMode;
  sceneStep: number;
  hasKey: boolean;
  hasModule: boolean;
  messages: GameMessage[];
}
```

Основные операции движка:

```ts
createInitialGameState(): GameState
submitCommand(state: GameState, command: string): GameState
restartGame(): GameState
```

Движок не должен импортировать React, обращаться к DOM, читать `localStorage` или выводить строки через `console.log()`.

Учебная цель: понять, как браузер загружает React-приложение и чем `main.tsx` отличается от CLI-точки входа.

Критерии готовности:

- `npm run dev` открывает приложение;
- `npm run build` создаёт production-сборку;
- `npm run typecheck` проходит;

Результат проверки:

### Этап 2. Выделение чистого игрового движка

**Статус: выполнен 30 августа 2026 года.** Игровые переходы вынесены в `src/features/game/engine` и больше не зависят от терминала, React, DOM или хранилища браузера. После переноса исходного текста на этапе 3 временная CLI-версия была удалена.

Задачи:

- отделить сюжетные переходы от `readline` и `console.log`;
- описать `GameState`, `GameMessage`, `InputMode` и команды пользователя;
- реализовать создание начального состояния;
- превратить каждое действие игрока в чистый переход `state -> newState`;
- сохранить все комнаты, ключ, энергомодуль, загадку, смерть и победу;
- не изменять входной объект состояния, а возвращать новый;
- покрыть основные переходы unit-тестами.

Учебная цель: иммутабельность, discriminated unions, чистые функции и отделение бизнес-логики от UI.

Критерии готовности:

- движок не зависит от React и Node terminal API;
- победный и смертельный маршруты проходят тестами;
- неправильные команды не изменяют игровой прогресс;
- после завершения доступна команда перезапуска.

Результат проверки:

- реализованы все шесть комнат, получение ключа и энергомодуля, загадка, смерть и победа;
- состояние и история сообщений обновляются иммутабельно;
- сообщения хранят типизированные ключи, поэтому на этапе 3 их можно переводить во время отображения;
- `getScene` скрывает уже недоступные действия и открывает действия, зависящие от инвентаря;
- восемь unit-тестов проверяют оба завершения, загадку, закрытую дверь, некорректные команды, инвентарь, перезапуск и иммутабельность;
- `npm test`, `npm run typecheck` и `npm run build` проходят.

### Этап 3. Типизированная локализация RU/EN

**Статус: выполнен 30 августа 2026 года.** Весь сюжет и временный интерфейс используют строгие словари RU/EN. Язык определяется по настройкам браузера, переключается без перезапуска и сохраняется по ключу `quest-game.locale.v1`.

Задачи:

- определить `Locale = "ru" | "en"`;
- составить единый union-тип `MessageKey`;
- перенести весь русский текст в `ru.ts`;
- подготовить полноценный английский перевод в `en.ts`;
- проверить через TypeScript, что в обоих словарях есть все ключи;
- реализовать подстановку параметров в сообщения;
- хранить в истории ключи, а не переведённые строки;
- синхронизировать атрибут `<html lang>`;
- сохранять выбор в `quest-game.locale.v1`.

Учебная цель: `Record`, `keyof`, `satisfies`, типобезопасные словари и Mantine `useLocalStorage`.

Критерии готовности:

- весь интерфейс и история консоли переключаются без перезапуска;
- отсутствующий перевод вызывает ошибку TypeScript;
- выбранный язык восстанавливается после обновления страницы;
- по умолчанию используется язык браузера, а при неподдерживаемом языке — русский.

Результат проверки:

- единый `MessageKey` объединяет ключи игрового движка и интерфейса;
- `ru` и `en` проверяются через `satisfies TranslationDictionary`, поэтому пропущенный или лишний ключ вызывает ошибку TypeScript;
- `translate` подставляет строковые и числовые параметры в шаблоны `{{parameter}}`;
- одна история сообщений отображается на обоих языках без изменения состояния игры;
- загадка принимает локализованные ответы `отражение` и `reflection`;
- Mantine `useLocalStorage` сохраняет язык, синхронизирует вкладки и восстанавливает значение после перезагрузки;
- `<html lang>` синхронизируется с выбранной локалью;
- временный `SegmentedControl` позволяет проверить RU/EN до создания финального `LanguageSwitcher` на этапе 7;
- браузерная проверка подтвердила переключение EN → RU, сохранение RU после reload, отсутствие переполнения на 390 px и отсутствие ошибок консоли;
- 15 unit-тестов, строгая проверка TypeScript и production-сборка проходят;
- временная CLI-версия и зависимость `tsx` удалены после полного переноса исходного текста.

- разместить название и короткий статус игры в Header;
- подготовить места для переключателей языка и темы;
- создать центральную область через Mantine `Container`, `Stack` и `Group`;
- прижать Footer к нижней границе на коротких экранах;
- добавить базовую адаптивность через responsive props Mantine и CSS Modules.

Учебная цель: композиция React-компонентов, compound-компоненты `AppShell`, Mantine style props, CSS Modules и семантический HTML.

Критерии готовности:

- страница корректно выглядит на ширине 320 px и на большом мониторе;
- Header и Footer не перекрывают игровую область;
- навигация с клавиатуры имеет видимый фокус.

Результат проверки:

- Header содержит название, статус движка и подготовленную зону настроек с временным RU/EN-контролом;
- Footer прижат к нижней границе короткого экрана и содержит локализованные подписи;
- Main автоматически учитывает высоту фиксированных панелей через AppShell offsets;
- при ширине 320 px Header заканчивается на 80 px, контент занимает диапазон 97–471 px, а Footer начинается на 488 px;
- при ширине 320 px и 1280 px горизонтальное переполнение отсутствует;
- переключатель языка остаётся нативной radio-группой, доступной с клавиатуры, а Mantine добавляет `focus-visible` outline;
- английская и русская версии помещаются в каркас без пересечений;
- ошибок и предупреждений в консоли чистого браузерного запуска нет;
- 15 unit-тестов, строгая проверка TypeScript и production-сборка проходят.

### Этап 5. Центральное консольное окно

**Статус: выполнен 31 августа 2026 года.** Чистый игровой движок подключён к React через `useReducer`, а весь сюжет теперь можно пройти в центральном Mantine-терминале без перезагрузки страницы.

Задачи:

- создать рамку терминала на основе `Paper` с заголовком и индикаторами окна;
- вывести историю сообщений через `ScrollArea`;
- визуально различать сюжет, ввод игрока, системные сообщения и ошибки;
- создать форму с Mantine `TextInput`, `Button`, `Group` и `Stack`;
- обрабатывать Enter через обычный `submit` формы;
- автоматически прокручивать историю к последнему сообщению;
- возвращать фокус в поле после каждой команды;
- менять подсказку ввода в зависимости от `InputMode`;
- блокировать ввод после конца игры и показывать Mantine `Button` Restart;
- добавить `role="log"` и подходящий `aria-live` для новых сообщений.

Учебная цель: контролируемые поля, события формы, `useRef`, осмысленный `useEffect` и доступность.

Критерии готовности:

- игру можно полностью пройти через веб-консоль;
- неверный ввод даёт понятное сообщение;
- история корректно прокручивается;
- управление возможно только с клавиатуры;
- экранный диктор получает новые сообщения без повторного чтения всей страницы.

Результат проверки:

- `useGame` служит тонким React-адаптером над чистыми функциями `submitCommand` и `restartGame`;
- терминал собран из `Paper`, `ScrollArea`, `TextInput`, `Button`, `Group` и `Stack`, а разные типы сообщений имеют отдельное визуальное оформление;
- обычная HTML-форма обрабатывает отправку с клавиатуры, меняет подпись и placeholder в зависимости от `InputMode` и очищает поле после команды;
- после обновления истории фокус возвращается к вводу, а после победы или смерти — к кнопке перезапуска;
- история автоматически прокручивается вниз и объявляет добавления через `role="log"` и `aria-live="polite"`;
- в браузере полностью проверены победный и смертельный маршруты, неверный выбор, неверный ответ на загадку и перезапуск;
- переключение RU/EN переводит уже показанную историю, не сбрасывая состояние игры;
- на ширине 320 px консоль помещается между Header и Footer без горизонтального переполнения;
- ошибок и предупреждений в консоли браузера нет;
- 17 unit-тестов, строгая проверка TypeScript и production-сборка проходят.

## 6. Правила реализации

Во время работы придерживаемся следующих правил:

1. Выполняем только один этап за раз.
2. Перед следующим этапом запускаем доступные проверки текущего этапа.
3. Игровая логика остаётся независимой от React-компонентов.
4. Не храним в состоянии значения, которые можно вычислить во время рендера.
5. Обновляем React-состояние функционально, когда новое значение зависит от предыдущего.
6. Не добавляем `useMemo`, `useCallback` или `React.memo` без измеримой причины.
7. Побочные эффекты используем только для синхронизации с внешними системами: DOM, `localStorage`, системная тема.
8. Статические данные и словари располагаем вне компонентов.
9. Избегаем массовых barrel-реэкспортов; импортируем напрямую из нужного файла.
10. Сначала используем подходящий компонент или хук Mantine и только затем создаём собственный аналог, если готового API недостаточно.
11. Компоненты Mantine импортируем из официальных package entry points; правило прямых импортов применяем к файлам нашего приложения.
12. Цвета, размеры, интервалы, радиусы, тени и типографика берутся из `docs/design-tokens.css`; сырые значения в компонентах запрещены.
13. Для light/dark различий используем семантические `--app-*` variables, а не проверки темы внутри JSX.
14. Каждая новая интерактивная возможность должна работать с клавиатуры.
15. Перед завершением этапа запускаем `npm run check`; безопасные исправления форматирования, линтинга и порядка импортов применяем через `npm run check:fix`.
