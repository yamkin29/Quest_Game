# TDD-методология для крупных поведенческих фич

Документ описывает процесс разработки (TDD, test-driven development), по которому ведутся крупные поведенческие фичи: новые игровые механики, команды, сценарии, правила переходов, изменения поведения хуков и компонентов. Инструкция для агента: получив такую задачу, работай по этому документу, не дожидаясь отдельного указания.

Методология **не обязательна** для визуальной полировки: подбор отступов, цветовых вариаций и одноразовые эксперименты можно делать без тест-фёрст — покрытие добирается при стабилизации (порог в `vite.config.ts` всё равно не даст забыть).

## 1. Суть подхода

Цикл из трёх шагов:

1. **Red** — пишем маленький тест, описывающий ещё не существующее поведение. Запускаем и убеждаемся, что он падает: это проверка, что тест работает и ловит отсутствие фичи.
2. **Green** — пишем минимальный код, чтобы тест прошёл. Не идеальный, а минимальный.
3. **Refactor** — убираем дублирование и приводим код в порядок; зелёные тесты остаются страховкой.

Три закона (Р. Мартин): не пишем продакшен-код без падающего теста; не пишем больше теста, чем нужно для падения; не пишем больше кода, чем нужно для прохождения. Из этого следует, что за итерацию добавляется ровно одно поведение.

Зачем это нужно: цель TDD — не метрики покрытия, а дизайн. Код, который легко тестировать, почти автоматически получается слабо связанным, а тесты становятся исполняемой спецификацией. Побочные эффекты — мгновенная обратная связь (секунды, а не минуты) и маленькие управляемые шаги.

Правила хороших тестов: на поведение, а не на внутренности; arrange–act–assert; быстрые, детерминированные, независимые друг от друга. Моков минимум — только на границы системы; в чистых функциях модели моки не нужны.

## 2. Уровни тестирования и их роли

| Уровень | Где | Окружение | Роль в TDD |
|---|---|---|---|
| Модель (чистые функции) | `src/entities/game/model/`, `src/shared/i18n/`, `src/app/theme/` | `node` (дефолт Vitest) | Основной TDD-цикл; тесты выполняются за миллисекунды |
| Хуки и компоненты | `src/features/`, `src/widgets/`, `src/pages/` | `jsdom` + Testing Library | TDD на уровне поведения компонента: «кнопка с ролью submit вызывает `onSubmit`» |
| E2E | `e2e/` (Playwright + axe) | браузер | Уровень приёмки: сценарий можно написать заранее, но цикл на нём не гоняем — медленно |

## 3. Процесс

### Шаг 0. Спецификация списком

До кода выписываем 3–7 строк «что должна делать фича» — прямо в задачу или в начало тестового файла комментариями. Пример для новой команды игры:

- `inventory` выводит список собранных предметов;
- без предметов выводит сообщение «пусто»;
- неизвестная команда игнорируется с подсказкой.

Этот список — backlog падающих тестов. За итерацию берём один пункт, не все сразу.

### Шаг 1. Red

Пишем один тест рядом с будущим кодом (тесты колокализованы с реализацией: `foo.ts` → `foo.test.ts`), в существующем стиле проекта — `describe`/`it` на английском, как в `getScene.test.ts`:

```ts
import { describe, expect, it } from "vitest";

import { runInventory } from "./runInventory";

describe("runInventory", () => {
  it("lists collected items", () => {
    const output = runInventory({ hasKey: true, hasModule: false });

    expect(output.messageKey).toBe("inventory.items");
    expect(output.items).toContain("key");
  });
});
```

Запускаем точечно и убеждаемся, что тест падает:

```bash
npx vitest run src/entities/game/model/runInventory.test.ts
```

Удобно держать во втором терминале `npm run test:watch` — watch-режим и есть движок цикла Red→Green.

### Шаг 2. Green

Пишем минимальную реализацию, тест становится зелёным. Для пользовательских текстов сразу добавляем ключи в словари — парность локалей страхует `src/shared/i18n/dictionaries.test.ts`.

### Шаг 3. Refactor

Убираем дублирование, упрощаем, переименовываем — под защитой зелёных тестов. Возвращаемся к шагу 1 со следующим пунктом списка.

Для компонентов тест пишется первым так же, но описывает видимое поведение через доступность-запросы Testing Library (`getByRole`, `getByLabelText` — они же улучшают a11y, что заодно подыгрывает axe-сканам в e2e). Для DOM-тестов нужно jsdom-окружение: по файлу через докблок `// @vitest-environment jsdom` — в проекте для этого паттерн суффикса `*.dom.test.ts` (см. `useLanguage.dom.test.ts`).

### Шаг 4. Гейты перед коммитом

- `npm run validate` — линтер + типы + все тесты + сборка (требование AGENTS.md).
- После крупных рефакторингов — `npm run check:react`.
- Тесты и реализация коммитятся вместе одним коммитом (`feat(game): ...`); падающих тестов в истории не оставляем. Отдельный `test:`-коммит уместен, только если тесты добавляются к уже существующему поведению.

## 4. Что писать первым для E2E (ATDD)

Для крупной фичи полезно сначала описать приёмочный сценарий в `e2e/`: «игрок находит ключ, вводит `inventory`, видит его в списке». Пусть сценарий висит красным, пока фича не готова, — это и есть определение готовности. Сам цикл Red→Green делаем на юнит- и компонентных тестах, e2e прогоняем в конце (`npm run test:e2e`).

## 5. Чек-лист агента

- [ ] Задача — крупная поведенческая фича? Если да, работаем по TDD, без напоминаний.
- [ ] Выписан список поведений (3–7 пунктов) до кода.
- [ ] Каждый пункт — одна итерация Red→Green→Refactor; тест перед реализацией виден падающим.
- [ ] Тесты на поведение, колокализованы с кодом, имена на английском.
- [ ] DOM-тесты помечены jsdom-окружением (паттерн `*.dom.test.ts`).
- [ ] Ключи локализации добавлены в оба словаря.
- [ ] Для крупной фичи написан приёмочный e2e-сценарий.
- [ ] Перед коммитом: `npm run validate` (+ `npm run check:react` после крупных рефакторингов).
