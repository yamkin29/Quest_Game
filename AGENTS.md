# Правила проекта

## UI

1. Используем Mantine v9 (`@mantine/core`, `@mantine/hooks`). UI строим на готовых компонентах Mantine, а не на самописных `div`/кнопках; хуки и утилиты берём из `@mantine/hooks`; тему настраиваем через `MantineProvider`, а не через глобальный CSS.
2. Документация по компонентам — через подключённый MCP-сервер `mantine`: сначала ищем props и примеры его инструментами `search_docs`, `list_items`, `get_item_doc`, `get_item_props` (у `get_item_props` аргумент — `name`, например `Button`).
3. Для сложных задач подключены user-скиллы: `mantine-form` (формы и валидация на `@mantine/form`), `mantine-combobox` (селекты и автокомплиты на Combobox), `mantine-custom-components` (кастомные компоненты через factory/Styles API).
4. Если MCP-инструменты `mantine` недоступны в сессии — fallback: типы в `node_modules/@mantine/core`, сайт [mantine.dev](https://mantine.dev) и [llms.txt](https://mantine.dev/llms.txt). Всегда учитываем, что в проекте Mantine v9.

## Git: организация и коммиты

### Организация изменений

- Один коммит — одна логическая задача (фича, фикс, рефакторинг, тесты). Несвязанные изменения разбиваем на отдельные коммиты.
- Перед коммитом всегда смотрим `git status` и `git diff`, в индекс добавляем только файлы, относящиеся к задаче.
- В репозиторий не должны попадать: артефакты сборки и тестов (`dist/`, `coverage/`, `test-results/`), `node_modules/`, `.DS_Store`, `.idea/`, секреты и `.env`-файлы. Если такой файл оказался в статусе — добавляем его в `.gitignore`, а не в коммит.

### Формат сообщений (Conventional Commits)

```
<type>(<scope>): <description>
```

- `type` — один из: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`.
- `scope` (опционально) — затронутая часть приложения: `game`, `ui`, `i18n`, `e2e`, `deps` и т.п.
- `description` — на английском, с маленькой буквы, в повелительном наклонении, без точки в конце. Примеры из истории: `fix: dictionary-driven locale labels and honest restart messages`, `test: add e2e suite with axe a11y scans and CI pipeline`.
- Если одной строки мало — добавляем тело после пустой строки (строки до 72 символов): что изменено и почему.

### Проверки перед коммитом

- При коммите автоматически работают git-хуки (husky): `pre-commit` через lint-staged исправляет форматирование staged-файлов (Biome) и проверяет типы (`tsc -b`), `commit-msg` проверяет формат сообщения (commitlint).
- Перед коммитом кода должен проходить `npm run validate` (линтер + типы + тесты + сборка). Точечное автоисправление форматирования — `npm run check:fix`.
- Для изменений только в документации (`*.md`) проверку кода можно не запускать.
- Проверки не отключаем (`--no-verify` запрещён): если проверка упала — чиним и коммитим заново.

### Правила для агента

- Коммитим только по явной просьбе пользователя; push — тоже только по явной просьбе.
- Без явного разрешения не переписываем опубликованную историю (`rebase`, `reset --hard`, `push --force`).
